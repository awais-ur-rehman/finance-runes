# Data, privacy and security

**Status:** active — these rules apply from the first commit
**Last updated:** 2026-11-12

The dataset is a person's complete financial life. Treat every design decision as if the data belonged to someone you respect, because it does.

## Principles

1. **Local by default, network by exception.** The app makes zero outbound connections in normal operation (NFR-020). A future feature that needs the network is opt-in, documented, and off by default.
2. **No telemetry, ever, by default.** No analytics, no crash uploads, no usage pings. If diagnostics are ever added, they are local files the user chooses to share.
3. **The user owns the bytes.** Export produces a documented format readable without this app (FR-081). Backups restore to an identical dataset (NFR-033).
4. **Fail closed.** A corrupt, newer, or unexpected dataset is reported and left alone. Never "repair" by guessing, never silently downgrade.
5. **Least data.** Do not store what the feature does not need. No full account numbers, no card numbers, no bank credentials.

## Repository rules

### Never commit

- Real bank statements, exports, screenshots showing real balances, or databases.
- Names, addresses, account numbers, IBANs, card numbers, or tax identifiers.
- Secrets: API keys, tokens, certificates, `.env` files, signing keys.
- Absolute paths from a developer's machine (`C:\Users\...`, `/Users/...`) in code, tests, fixtures or docs.
- Logs or traces from a real session.

### Fixtures

- Synthetic or irreversibly anonymised. `Example Bank`, `Sample Payee`, amounts that are obviously invented.
- Generated by a script where possible, so they can be regenerated and reviewed.
- Small: enough rows to exercise the parser, not a real month.

### Pre-push check

```bash
git diff --cached | rg -n "secret|token|password|api[_-]?key|/Users/|C:\\\\Users|BEGIN .*PRIVATE KEY"
```

Read the staged diff end to end before every push. Automated scanners miss context.

## Threat model (v1)

| Threat | In scope? | Mitigation |
| --- | --- | --- |
| Another local user reading the dataset | Partly | Rely on OS file permissions and disk encryption; document it plainly (Q-04) |
| Malware on the machine | No | Out of scope; the app cannot defend a compromised OS |
| Malicious import file | **Yes** | Defensive parsers, fuzzing, size limits, no code execution, no path traversal in attachments |
| Backup file tampering | **Yes** | Integrity checks on restore; version gate; no partial restore |
| Data loss from crash | **Yes** | Transactional writes, WAL, pre-migration backup (NFR-003, FR-082) |
| Data loss from user error | **Yes** | Undo, confirmation on destructive actions, retention of backups |
| Supply-chain compromise | **Yes** | Committed lockfile, minimal dependencies, review of new crates, `cargo audit` in CI |
| Network exfiltration | **Yes** | Zero network calls in normal operation, verified by test |

## Handling user input

- **Parsers are hostile-input code.** Bound file size, reject unexpected encodings, never panic. A malformed row is an error with a row number, not a crash (NFR-023).
- **Attachments** are content-addressed and validated by magic bytes, not by extension. Never follow a path from a file.
- **No `unsafe` in `finance-core`**; `unsafe` elsewhere requires a `// SAFETY:` comment.
- **Format strings and SQL** are parameterised. No string-built SQL, ever.

## Logging

- Structured, local, and redacted by construction.
- Never log amounts, payees, notes, account names, or file paths from the user's dataset (NFR-024).
- Log identifiers (transaction IDs) rather than contents when diagnosing.
- Logs rotate and are deletable from the app.

## Backups

- Created with a consistent snapshot mechanism, never a copy of a live file (ADR-0004).
- Stored outside the working directory, with retention (FR-083).
- A pre-migration backup is taken automatically and kept until the migration is confirmed (FR-082).
- Restore validates integrity and version before touching the current dataset.

## If something goes wrong

1. **Rotate** any exposed credential immediately — before investigating.
2. **Contain**: stop the release, do not publish the artefact.
3. **Tell** the maintainer privately (see [`SECURITY.md`](../../SECURITY.md)).
4. **Fix**, then write the post-mortem in the PR, not in a public issue.
